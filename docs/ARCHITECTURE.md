# Cortex — архитектура

Документ описывает принятые решения и их причины. README отвечает на вопрос
«как пользоваться», этот файл — «почему устроено именно так».

---

## 1. Модель слушателя: один шлюз

**Решение.** Корпоративную группу слушает один бот — `@Cortex` с выключенным
privacy mode. Боты-сотрудники используются только для отправки: ответ уходит
их токеном, поэтому в чате видно, кто именно принёс результат.

**Почему.** Telegram по умолчанию включает ботам privacy mode: в группе бот
видит только команды и адресованные ему сообщения. Дополнительно бот вообще не
получает сообщения от других ботов. Если бы каждый сотрудник слушал сам,
получилось бы N polling-соединений, N раз одна и та же история чата и
невозможность агентам «слышать» друг друга.

**Компромисс.** Персональный листенер всё же поддержан: `listen: true` в реестре
или `/listen <name> on`. Gateway поднимает для сотрудника отдельный `Dispatcher`
без перезапуска сервера. По умолчанию выключено.

**Следствие.** Один и тот же `Router` нельзя подключить к двум `Dispatcher`.
Поэтому роутеры создаются **фабриками** (`build_command_router(deps)`), а не
объявляются на уровне модуля.

## 2. Транспорт: long polling

Webhooks требуют публичный HTTPS-домен и сертификат. На Windows Server без
внешнего адреса это лишний слой (туннель, обратный прокси, продление
сертификата) ради нагрузки в десяток сообщений в минуту. Polling асинхронный и
главный поток не блокирует.

Переезд на webhooks затрагивает только `telegram/gateway.py`.

---

## 3. Разделение слоёв

| Пакет | Знает про | Не знает про |
|---|---|---|
| `telegram/` | aiogram, чаты, ботов | subprocess, файловую систему проектов |
| `runtime/` | процессы, таймауты, stderr | Telegram, чаты |
| `workspace/` | файлы, пути, песочницу | Telegram, процессы агентов |
| `tools/` | контракт `<action>` | откуда пришла задача |
| `orchestrator.py` | всех троих | детали каждого |

Правило проверяется просто: `runtime/runner.py` не импортирует `aiogram`, а
`telegram/routing.py` не импортирует `asyncio.subprocess`. Благодаря этому
маршрутизация, песочница и парсер тестируются без сети и без Telegram.

`cortex/telegram/__init__.py` намеренно пуст: `hr.py` использует `bot_pool`,
а `hiring.py` использует `hr` — реэкспорт `Gateway` на уровне пакета замкнул
бы импорты в кольцо.

## 4. Динамический HR

`employees_registry.json` — единственный источник правды о штате. Владелец
файла — `EmployeeRegistry`, все записи атомарные (`tmp` + `os.replace`) под
`asyncio.Lock`, с `.bak` перед каждой перезаписью: в файле лежат боевые токены.

**Порядок найма важен:**

1. сгенерировать должностную инструкцию (сотрудник без инструкции бесполезен);
2. добавить запись в реестр;
3. проверить токен через `getMe`;
4. при отказе Telegram — **откатить** найм целиком.

Обратный порядок оставлял бы в реестре мёртвые души при неверном токене.

**Реестр не создаёт ботов.** Telegram Bot API этого не позволяет — только
BotFather. Поэтому найм диалоговый и ведётся в личке: токен не должен попасть
в общий чат.

## 5. Изоляция проектов

Каждый проект — папка в `projects/` с манифестом `.plexus.json`. Агенту
передаётся `cwd` его проекта, и он видит только этот код.

Защита пути — в одном месте, `WorkspaceManager.resolve_path()`:

```
base = project.path.resolve()
resolved = (base / relative).resolve()
if resolved != base and base not in resolved.parents: отказ
```

Через него проходят `execute_command` (cwd), `send_file` (путь к файлу) и любой
будущий инструмент, работающий с файлами. `..`, абсолютные пути и симлинки
наружу отсекаются `resolve()` до исполнения. Отключается только явным
`security.allow_escape_workspace: true`.

Имя проекта с путём внутри (`../../etc`) отклоняется, а не вычищается молча:
тихая нормализация в `etc` создала бы не тот проект, который просили.

## 6. Планировщик

Две гарантии:

- **глобальный семафор** — не больше `max_parallel_tasks` процессов `agy`
  одновременно (иначе три параллельных `npm install` кладут сервер);
- **лок на проект** — задачи внутри одного проекта строго последовательны.
  Два агента не правят один репозиторий одновременно. Разные проекты идут
  параллельно.

Обработчик Telegram не ждёт результат: задача уходит в `asyncio.create_task`,
иначе polling встал бы на всё время работы агента (минуты).

## 7. Контракт Tool Use

Агент возвращает текст, внутри которого могут быть блоки:

```
<action>
{"tool": "execute_command", "args": {"command": "git status"}}
</action>
```

Текст вне блоков — реплика в чат, блоки — действия. Порядок исполнения сверху
вниз, **до первой неудачи**: следующие действия обычно опираются на результат
предыдущих, продолжать после провала опаснее, чем остановиться.

Парсер (`tools/parser.py`) рассчитан на неаккуратность живых моделей:

- ```` ```json ````-обёртка внутри блока;
- трейлинг-запятые;
- синонимы ключей: `tool` / `action` / `name`, `args` / `params` / `arguments`;
- плоская форма `{"tool": "execute_command", "command": "ls"}`;
- массив объектов в одном блоке.

Сломанный блок не отменяет остальные — ошибки возвращаются отдельным списком и
уходят в чат отдельным сообщением.

**Политика доступа** проверяется в `ToolRegistry.dispatch` до вызова
инструмента: персональный список из реестра важнее `config.yaml → tools`.
Поэтому `web_research` у Synapse, а `execute_command` — нет.

## 8. Synapse

Единственный сотрудник с сетевым доступом. Весь HTTP компании сосредоточен в
`agents/synapse.py`, а не размазан по инструментам: расширять периметр придётся
осознанно, правя один файл.

Отсутствие `execute_command` у Synapse — не пробел в конфиге, а его должность.
Инженеров в компании много, человек, который смотрит наружу, — один.

## 9. Обработка ошибок

| Что упало | Что происходит |
|---|---|
| `agy` вернул ≠ 0 | `AgentRunError` со `stderr`, кодом и временем → отчёт в чат |
| `agy` завис | снятие процесса (terminate → kill через 5 с) → отчёт |
| бинарник не найден | подсказка про PATH и `config.yaml`, а не `FileNotFoundError` |
| инструмент упал | `ToolResult.failure`, остальные действия отменяются |
| битый HTML от агента | повторная отправка без разметки |
| повреждён реестр | Cortex отказывается его перезаписывать и говорит об этом |

Всё, что наследует `CortexError`, — ожидаемая ситуация: превращается в
аккуратное сообщение. Остальное логируется с трейсбеком и тоже уходит в чат,
но как «неизвестный сбой».

Ни одна из этих ошибок не роняет процесс: polling продолжается.

---

## 10. Безопасность

`SecurityMiddleware` стоит **перед всеми** обработчиками — ни один хендлер не
может случайно оказаться публичным. Проверяется тройка: чат разрешён,
отправитель — CEO или бот из реестра, бот активен.

Посторонним Cortex не отвечает вообще. Ответ вида «доступ запрещён»
подтверждает, что по этому адресу живая система.

Уволенный бот теряет доступ немедленно: `authorize` смотрит на `active`.

---

## 11. Что осознанно не сделано

- **Webhooks** — не нужны без публичного домена; слой заменяем.
- **База данных** — реестр и состояние это JSON, который CEO может открыть и
  починить руками. Для десятка сотрудников БД была бы лишней зависимостью.
- **Очередь на брокере** (Redis/RabbitMQ) — при одном сервере `asyncio` +
  семафор решают ту же задачу без инфраструктуры.
- **Память агентов между задачами** — сейчас контекст это история чата плюс
  должностная инструкция. `update_system_prompt` даёт долговременную память
  там, где она осмысленна.
- **Групповые диалоги агент↔агент** — Telegram не даёт ботам видеть друг друга
  в группе. Реализуемо через Cortex как посредника, но это отдельная функция,
  а не побочный эффект.
