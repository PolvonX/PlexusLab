# Claude-family model fallback on quota — design

**Дата:** 2026-08-16
**Статус:** approved

## Проблема

Единственная модель мозга (`brain.model: sonnet`, драйвер `claude`) — точка входа для
каждого свободного сообщения CEO (`cortex/brain/agent.py::_run_loop`, вызывает
`deps.runner.run()` напрямую, в обход `orchestrator.dispatch()`). Когда эта модель
упирается в квоту, `_run_loop` ловит `AgentRunError`, шлёт отчёт об ошибке в чат и
ничего больше не делает — ни ретрая, ни фоллбека. Поскольку мозг — единственный
обработчик, каждое следующее сообщение CEO повторяет тот же провал, пока квота не
сбросится (часы) — система выглядит полностью вставшей.

Отдельно, `orchestrator.dispatch()` (сотрудники, `self_execute_task`) уже умеет ждать
кулдаун и повторять ту же модель (см. `_MAX_AUTO_RETRIES`, `_retry_after_cooldown`,
добавлено ранее в этой же сессии) — но это тоже не помогает, если кулдаун — часы, а
не минуты.

## Требования

- Модели-фоллбеки — только внутри семьи Claude (sonnet → haiku). Кросс-вендорный
  фоллбек (gpt-4o-mini и т.п.) обсуждался и отклонён: гайдрейлы и системные промпты
  проекта рассчитаны на конкретную линейку моделей, смена вендора меняет поведение
  непредсказуемо.
- Переключение на фоллбек — сразу при retryable-ошибке, без ожидания кулдауна: это и
  есть решаемая боль («весь конвейер встаёт на часы»).
- Покрыть оба места, где реально вызывается модель: `brain/agent.py` (мозг, основная
  точка боли) и `orchestrator.py` (сотрудники/self_execute_task, уже частично
  прикрыто кулдауном — фоллбек добавляется как более быстрая альтернатива).
- Если фоллбеки исчерпаны/не настроены — откатываемся к уже существующему поведению
  (кулдаун-ретрай для сотрудников; отчёт об ошибке для мозга, как сейчас).

## Решение

### Конфиг — переиспользуем абстракцию драйверов

Вместо нового механизма подмены `{model}` в шаблоне команды — новый driver-entry,
копия существующего с другим `--model`:

```yaml
agent_runner:
  drivers:
    claude:
      command: 'claude.cmd -p ... --model sonnet {session_flag}'
      ...
    claude_haiku:
      command: 'claude.cmd -p ... --model haiku {session_flag}'
      prompt_via_stdin: true
      env: {}

brain:
  driver: "claude"            # уже есть неявно через agent_runner.driver; уточняем
  fallback_drivers: ["claude_haiku"]
```

Для сотрудников — аналогично, `agent_runner.fallback_drivers: [...]` (список имён
драйверов из `agent_runner.drivers`), применяется в `orchestrator.dispatch()`.

### Логика — новый шаг между "упал" и "ждать/сдаться"

И в `brain/agent.py::_run_loop`, и в `orchestrator.py::dispatch()` — при
`AgentRunError` с `retry_after is not None` (уже размеченная ранее квота-классификация
из `runner.py::_parse_retry_after`):

1. Если для текущего вызова есть неиспользованный fallback-драйвер — пробуем его
   немедленно, **без `--resume`** (свежая сессия: резюме через смену модели не
   гарантированно поддерживается CLI, риск конфликта состояния).
2. Если fallback тоже упал retryable-ошибкой — пробуем следующий в списке (если есть).
3. Если fallback-драйверов больше нет (список исчерпан или изначально пуст) —
   поведение как сейчас: `orchestrator.py` ждёт кулдаун и повторяет основную модель
   (существующий `_retry_after_cooldown`); `brain/agent.py` шлёт отчёт об ошибке в чат
   (существующее поведение, не меняется).
4. Успешный ответ от fallback-модели доставляется в чат как обычно — CEO не обязан
   знать, что ответила другая модель (не добавляем в сообщение пометку "отвечала
   haiku", если не попросят отдельно — не в скоупе).

### Границы

- Не трогаем `risk.py`, `context/builder.py`, копирайт-политику — вне скоупа этой
  задачи и явно нежелательно (обсуждалось и отклонено ранее в сессии).
- Не добавляем фоллбек на других вендоров.
- Не переносим брейн на `orchestrator.dispatch()` — слишком большой рефакторинг вне
  запроса; фоллбек добавляется в существующую структуру `_run_loop` как есть.
